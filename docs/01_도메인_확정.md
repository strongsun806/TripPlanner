# 도메인 확정 — 국내·해외 여행 플래너 (가칭 TripPilot Agent)

> 작성일 2026-11-18 · 1일차 기획 검증용 (16시 마감)
> 2회차 프로젝트 TripPilot(RAG 여행 플래너)의 도메인을 이어 간다. 2회차 Vector DB 는 심화 F3022 에서 재사용한다.

## 1. 한 줄 정의

사용자가 말한 **목적지 · 날짜 · 시간대 · 선호**를 받아, 외부 API 로 후보 장소와 날씨를 확인하고
**제약(비 · 시간창)을 만족하는 하루 일정**을 제안한다. 맞지 않으면 실내 장소나 다른 시간대로 재계획한다.

## 2. 외부 API (3종, 호출 확인 완료 2026-11-18 11:58 — `api_check.py`)

| 역할 | API | 주는 정보 | 범위 | 인증 | 이용 조건 |
|---|---|---|---|---|---|
| 후보 목록 (F3002) | Geoapify Places API | 관광지 · 박물관 · 공원 등 이름, 좌표, 카테고리, place_id | 전 세계 | API 키 | 무료 플랜 하루 3,000 크레딧(단순 요청 1건 = 1크레딧), 초당 5건, 출처 표기 필요 |
| 판단 근거 (F3003) | Visual Crossing Timeline API | 일별 강수확률 · 최고기온 (최대 15일 예보) | 전 세계 | API 키 | 무료 플랜 하루 1,000 레코드. **조회한 날짜 수만큼 레코드를 쓰므로** 필요한 날짜만 요청한다 |
| 보조 정보 (F3004) | 카카오 로컬 키워드 검색 | 주변 식당 · 카페 이름, 주소, 카카오맵 링크 | 국내 | REST API 키 | 키워드로 장소 검색 하루 100,000건 (카카오 디벨로퍼스 > 앱 > 통계 > 쿼터 > 일간 쿼터, 2026-11-18 확인, 매일 00:00 초기화) |

### 선정 과정에서 바꾼 것
- 날씨는 처음에 **Open-Meteo**(키 불필요, 16일 예보)를 골랐으나 교육장 네트워크에서 연결이 강제 종료되어
  (ReadTimeout → ConnectionResetError) **Visual Crossing** 으로 교체했다. 시연 환경 기준으로 동작하는 쪽을 택했다.
- 기상청 단기예보 · 관광공사 TourAPI 는 국내 전용이고 공공데이터포털 승인 대기가 있어, 필수 3종에서는 빼고
  **국내 보강용 후보**로 남긴다 (승인되면 국내 후보 보충 Tool 로 추가 — F3002 "다른 API 로 보충" 조항).

### 국내 / 해외 처리
- 후보 · 날씨는 전 세계 공통 API 라 같은 Tool 로 처리한다.
- 보조 정보는 국내는 카카오 로컬, 해외는 Geoapify 의 음식점 카테고리로 보충한다.
  해외 보조 정보는 후보와 출처가 같으므로, F3004 검증 시나리오는 국내(카카오)로 잡는다.
- Geoapify 해외 장소명은 현지어로 온다(예: 오사카 → 일본어). 표시용 이름은 `name:ko` → `name:en` → `name` 순으로 고른다.

## 3. Tool 결과를 제약과 비교해야 답할 수 있는 요청 (3개 이상)

| # | 대표 요청 | 추출 조건 | Tool 순서 | 판단 | 재계획 |
|---|---|---|---|---|---|
| R1 | "다음 주 토요일 오사카, 오후에 야외 위주로 돌고 싶어. 비 오면 곤란해" | 기준: 날짜 · 오후 / 선호: 야외 / 제약: 비 X | 후보 → 날씨 | 그날 강수확률 ≤ **50%** | 기준 초과면 **실내 카테고리(박물관 · 쇼핑 등)로 후보 재구성** |
| R2 | "이번 주말 서울 종로, 2시부터 6시까지 걷기 좋은 곳, 저녁 먹을 곳도" | 기준: 날짜 · 14:00 / 선호: 종로 · 도보 / 제약: 18:00 종료 | 후보 → 날씨 → 주변 식당 | 후보 간 직선거리(좌표로 계산) × 우회 계수 1.3 ÷ 도보 4 km/h 로 **이동 시간 합**을 구해 4시간 안에 드는지 | 안 들면 반경을 줄여 후보 재구성 |
| R3 | "3주 뒤 제주에서 하루, 바다 쪽으로" | 기준: 날짜(3주 뒤) / 선호: 해변 | 후보 → 날씨 | 예보 범위(15일) 밖 → **날씨 판단 보류**를 응답에 밝힘 | 재계획하지 않음 (다시 해도 결과 같음) |

- 체류 시간처럼 **API 로 확인할 수 없는 값은 지어내지 않는다.** 이동 시간은 API 가 준 좌표에서 계산하고,
  "늦어도 몇 시에 마지막 장소로 출발해야 하는지"처럼 역산한 기준으로 제시한다 (F3008).

### Tool 없이 LLM 만으로 답하면 틀리는 점 (기획 검증 2.7)

| # | LLM 만으로 답하면 | Tool 이 있어야 하는 이유 |
|---|---|---|
| R1 | "가을 오사카는 대체로 맑다" 같은 계절 일반론으로 야외 일정을 짠다 — 2026-11-18 실제 예보는 강수확률 100% 였다 | 그날 그곳의 **실제 강수확률**은 get_weather 로만 알 수 있다 |
| R2 | 장소 사이 거리와 이동 시간을 짐작으로 적고, 없어졌거나 실재하지 않는 식당을 추천할 수 있다 | 좌표(search_places)로 이동 시간을 계산하고, 식당은 search_nearby_food 의 실제 결과만 쓴다 |
| R3 | 3주 뒤 날씨를 아는 것처럼 단정한다 | 예보 범위(15일) 밖이라는 사실 자체가 get_weather 의 OUT_OF_RANGE 로 드러난다 |

### 그 밖에 정해 둔 요청
- **재계획 상한 도달**: "다음 주 내내 오사카, 비 안 오는 날 야외로" → 날짜를 바꿔 가며 재계획, **3회**에서 멈추고 조건 조정을 되묻는다.
- **되묻기**: "6시 전에 끝나야 해" (목적지 · 날짜 없음) → Tool 을 부르기 전에 되묻는다.
- **Tool 불필요**: 인사, 사용법 질문 → 계획 단계를 건너뛴다.
- **Tool 실패**: 카카오 키 누락 상태로 R2 → 식당 없이 일정만 제시하고 실패 사유를 알린다.

## 4. 저장 · 관리할 결과물 — 여행 일정

| 필드 | 예 |
|---|---|
| plan_id | 1 |
| place_name | 오사카성 |
| city | 오사카 |
| visit_date | 2026-11-28 |
| start_time / end_time | 14:00 / 16:00 |
| lat / lon | 34.6873 / 135.5262 |
| created_at | 2026-11-18T12:00:00 |

- 저장 · 목록 · 상세 · 수정 · 삭제 (F3015 · F3016). 1일차 실습 step5 CRUD 구조를 그대로 확장한다.
- 같은 날짜에 시간이 겹치는 일정이 있으면 **저장은 하되 겹치는 일정을 함께 알린다.**

## 5. 위험 도메인 여부

여행은 건강 · 금융처럼 판단이 위험한 도메인이 아니므로 면책 안내는 두지 않는다.
단, 날씨는 예보이므로 응답에 "예보 기준"임을 표시한다.
